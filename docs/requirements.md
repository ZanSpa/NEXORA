# NEXORA — Requisitos iniciales

Proyecto: NEXORA
Institución: CBTIS 230
Documento: Requisitos iniciales del sistema
Versión: 0.1
Estado: Borrador de planificación

1. Propósito

NEXORA busca centralizar herramientas e información escolar en una plataforma digital para facilitar la organización y consulta de actividades de la comunidad educativa.

El proyecto comenzará con un prototipo visual que permitirá explorar la estructura, la navegación y las funciones principales antes de iniciar el desarrollo del sistema.

2. Usuarios objetivo

- Estudiantes: consultarán horarios, tareas, fechas importantes y avisos escolares.
- Docentes: podrán consultar o, en futuras versiones, gestionar información relacionada con sus actividades escolares, según los permisos definidos.
- Comunidad escolar: podrá acceder a la información que le corresponda de acuerdo con su función y los permisos establecidos.

3. Requisitos funcionales propuestos

ID| Requisito| Prioridad
RF-01| Mostrar un panel principal con un resumen de la actividad escolar.| Alta
RF-02| Permitir consultar horarios de clases.| Alta
RF-03| Mostrar tareas, pendientes y fechas de entrega.| Alta
RF-04| Presentar un calendario con fechas importantes.| Alta
RF-05| Mostrar avisos y eventos escolares.| Alta
RF-06| Permitir navegar entre las secciones desde un menú claro.| Alta
RF-07| Explorar perfiles y permisos diferentes para estudiantes y docentes.| Media
RF-08| Evaluar funciones para registrar o actualizar información escolar.| Media

Las prioridades son provisionales y deberán validarse con usuarios potenciales y con los requisitos del concurso.

4. Requisitos no funcionales

- Usabilidad: la interfaz debe ser comprensible y fácil de navegar.
- Accesibilidad: los textos, controles y contrastes deben facilitar la lectura y la interacción.
- Adaptabilidad: el diseño debe contemplar celulares y computadoras.
- Privacidad: los datos personales y escolares deberán manejarse con medidas de protección adecuadas.
- Seguridad: una futura implementación deberá contemplar autenticación y permisos cuando sean necesarios.
- Mantenibilidad: el proyecto deberá organizarse y documentarse para facilitar futuras modificaciones.

5. Alcance del primer prototipo

La primera versión visual incluirá:

1. Pantalla principal o dashboard.
2. Vista de horario escolar.
3. Sección de tareas y pendientes.
4. Calendario de fechas importantes.
5. Sección de avisos escolares.
6. Navegación entre las secciones.

El prototipo podrá utilizar información ficticia de demostración. No requerirá inicialmente cuentas reales, una base de datos funcional ni información personal de estudiantes.

6. Fuera del alcance inicial

Quedan pendientes de evaluación:

- Inicio de sesión y administración de cuentas.
- Sincronización automática de horarios.
- Publicación oficial de avisos.
- Notificaciones.
- Integración con plataformas institucionales.
- Almacenamiento de datos reales.

Estas funciones no se considerarán implementadas hasta que se definan sus requisitos y se desarrollen y prueben.

7. Criterios de aceptación del prototipo

El prototipo inicial se considerará listo para una primera evaluación cuando:

- Las seis vistas o funciones previstas estén representadas.
- Se pueda comprender la navegación principal.
- El diseño sea legible en una pantalla móvil y en una computadora.
- Los usuarios de prueba puedan identificar dónde consultar las funciones principales.
- Se recopilen comentarios para decidir qué mejorar.

8. Validación pendiente

Antes de cerrar los requisitos, se investigarán las necesidades de estudiantes y docentes mediante preguntas breves, entrevistas o pruebas del prototipo.

No se considerarán confirmadas las necesidades ni la utilidad de las funciones hasta contar con evidencia.

9. Próximos pasos

1. Revisar los requisitos del concurso de prototipos.
2. Investigar las necesidades de la comunidad escolar.
3. Ajustar y priorizar los requisitos.
4. Diseñar los primeros bocetos de la interfaz.
5. Crear el prototipo visual.
6. Evaluarlo y documentar las mejoras.
